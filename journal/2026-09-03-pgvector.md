# 2026-09-03 — The first real index, and two failures that only a database could produce

`tearline` now verifies a live PostgreSQL with `pgvector` and row-level security. Six live tests,
run in CI against a service container, because there is no local Postgres.

Three CI runs, three genuine defects. None was reachable from a fixture.

## 1. A parameter placeholder in SET

`SET LOCAL tearline.principal_tenant = $1` is a syntax error: PostgreSQL does not accept
placeholders in `SET`. `set_config(name, value, is_local => true)` is the parameterised equivalent.

Interpolating the tenant into the SQL string would also have worked, and is not a trade worth
making in a tool whose subject is access boundaries.

## 2. The policy was never applied — and everything looked right

The second run passed two tests it should have failed. The suite connected as `postgres`, and **a
superuser bypasses row-level security entirely**. `FORCE ROW LEVEL SECURITY` does not change that:
FORCE binds the table *owner*, not a superuser.

So every retrieval came back correctly filtered — because the caller only asked for their own
tenant's rows anyway — and the adapter reported that the boundary held.

That is the worst failure this adapter could have. Not a wrong answer: a confident, right-looking
answer produced by never testing the thing under test. It is the same shape as `single-principal-
probe`, which forbids "no leak detected" from a one-identity probe, and I had built the database
equivalent without noticing.

The adapter now queries `pg_roles` and refuses such a connection by default.

## 3. Which forced the design to split

Refusing privileged connections broke the propagation axis, and the reason is worth keeping.

Reading every chunk means seeing rows **no principal can see** — precisely the population where a
mislabelling hides. A policy-filtered read only ever shows rows someone is already permitted, which
is the one place a wrong tenant tag is invisible. So the propagation axis needs a connection that
*can* bypass the policy, and the differential axis needs one that *cannot*.

Two connections with opposite privileges. That is not an inconvenience of the adapter; it is what an
audit of this backend actually requires, and the single-connection design was silently doing one of
the two badly.

## 4. And my own test forbade a legitimate pattern

The last failure was mine. `test_the_engine_enforces_the_boundary` asserted the two principals'
result sets do not intersect. They should: the shared handbook is stored for both tenants, and a
document shared across tenants is the commonest legitimate pattern in any shared corpus —
`wrong-tenant-tag`'s negative set names it and forbids flagging it.

I had written a test demanding the exact failure my own scenario forbids. It now asserts what
matters: no acme-only row reaches globex.

## What the backend establishes, and what it does not

The test carrying the argument is `test_engine_enforcement_does_not_catch_a_propagation_fault`. The
engine guarantees the policy is *applied*; it guarantees nothing about whether the stored tenant is
the one the source document has. The faulted index is served faithfully and quickly to the wrong
tenant while every database-level control behaves correctly.

That is the case for this tool on an engine-enforced backend, and it is now demonstrated against a
real database rather than argued from a fixture.

## The Qdrant side, added the same day

Both backends now run in CI, ten live tests between them. Qdrant needed no corrections, which is
itself informative: its adapter has nothing to get wrong about privilege, because the store enforces
nothing. All the subtlety on the Postgres side came from the engine having opinions.

`retrieve_unfiltered` is the piece worth keeping. It issues the same query with the tenant clause
omitted and returns another tenant's points, correctly and quickly — demonstrating the trust model
rather than asserting it. On Postgres the equivalent query returns nothing a principal may not see.

One distinction the untagged test records: Qdrant's filter excludes an untagged point *because it
is written as a positive match*. Written as an exclusion — everything whose tenant differs — it
would admit it, which is `untagged-chunk`'s naive variant, and nothing in the store would object.
