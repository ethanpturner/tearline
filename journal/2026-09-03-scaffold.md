# 2026-09-03 — Scaffolding tearline

Second of the three projects. Design documents only.

## Why this one is worth building

Of the four gaps surveyed, this is the only genuinely empty field. OWASP's RAG Security Cheat Sheet
prescribes three controls — per-chunk access-control metadata, cryptographically signed source
attribution, and regular cross-tenant testing to verify zero cross-boundary retrieval — and names no
tool for any of them. The maintained `Awesome-Trustworthy-RAG` bibliography, organised across six
trust dimensions by someone with every incentive to include such work, has no entry on access
control, cross-tenant leakage, ACL drift, or chunk provenance.

The surrounding tools each answer a neighbouring question. Vector stores enforce the tag they were
handed and never ask whether it is true. Authorization engines decide whether a principal may call a
tool, which the application must remember to ask, and whose honest answer during a confused-deputy
retrieval is yes. Red-teaming harnesses drive adversarial text at a chat endpoint. Evaluation
frameworks score whether retrieved text was relevant, never whether it was permitted.

Nothing sits in the middle and asks whether the corpus, the index, and the source system's
permissions agree.

## Decisions that took the most thought

**DEC-002, reporting by identifier and never by content.** This started as a privacy nicety and
turned out to be the sharpest decision in the set. The tool's output is a report about a
confidentiality failure, and that report gets pasted into tickets and stored in CI logs — systems
with weaker controls than the index it came from. **A report that quotes the leaked material is
itself a leak**, and one that escapes the boundary the tool exists to police.

It is also unnecessary, which is what makes it easy to accept: every question the tool asks is
answerable from identifiers and metadata. The consequence I had to accept is that a reader cannot
judge severity from the report alone — which is correct, since severity depends on what was
disclosed, and that decision belongs to someone looking at the content under proper authority rather
than to whoever the scanner emailed.

Recorded as a data-model rule rather than only a decision: no object has a field holding chunk text,
and none may be added.

**DEC-008, under-retrieval as a finding.** The obvious tool looks for leaks. But where entitlement
filtering runs after an approximate nearest-neighbour scan, a selective policy can return nothing
while matching content exists — confidentiality holds, completeness fails silently. And the
generation step does not error on an empty context; it answers anyway from parametric memory, with
no signal to the user.

So a leak-only tool would score that system as perfectly secure. Both directions are measured and
neither is subordinate. The honest limit is that under-retrieval needs an authored entitlement map
to know what should have come back, so it is fully measurable against fixtures and only partially
against a production index.

**DEC-003, no `public` value in the enum.** The natural filter — exclude chunks whose tenant differs
from the caller's — admits every chunk that has no tenant at all. Rather than write a rule against
that, the model has no way to express it: `EntitlementState` is `stated` or `unknown`, with no
permissive value to default to. A genuinely public document is `stated` with the source system's own
public marker.

**DEC-010, no backend abstraction before the second backend.** The stores are not interchangeable in
the way an abstraction implies. Where the engine enforces the policy, an application that forgets its
filter still cannot cross the boundary and the residual risk is completeness. Where the tag is
application-supplied, a mislabelled chunk is served correctly and quickly to the wrong caller. One
interface over both would report the same verdict for very different failure modes and would
encourage the assumption that the engine is on the operator's side.

The first two backends are chosen for that contrast rather than for popularity.

## The scenario that decides whether this is a real tool

`boundary-crossing-chunk`: a chunk spanning a restricted appendix and a public body. **The source
system does not determine the answer** — the document has one ACL, and chunking has manufactured a
question the source never answered. The correct output is `unverifiable`.

It is also the case most likely to be abused, since the evaluation plan's third divergence category
is "genuine ambiguity" and this is the obvious place to dump anything inconvenient. Named in both the
plan and the registry for that reason.
