# 2026-09-03 — The first fixture, and the two things it settled

Built `wrong-tenant-tag` with its clean twin. Authoring found two design questions the plan had not
answered and changed the scenario layout.

## One fault, two findings

The fixture plants a single mislabelled chunk: `c-0022` comes from a `globex` document and the index
tags it `acme`. That one field produces two different failures in two different principals — the
acme engineer receives another tenant's content, and the globex engineer stops receiving its own.

I did not design it that way; it fell out of writing the smallest realistic fault. It is the best
possible argument for DEC-008. A leak-hunting tool finds the first and reports the second as
healthy, so the tenant whose data was withheld sees no finding at all and their system quietly
answers from less context than it should have.

Worth stating what did *not* go wrong: the retrieval layer behaved correctly throughout. It enforced
the tag it was handed, promptly and precisely. The tag was wrong. Everything that tests the
retrieval layer's *behaviour* passes this scenario, and that is the gap the project exists in.

## What authoring settled

**DEC-011 — relevance is given data.** A probe needs to know which chunks a search returns before
filtering. Deriving that needs chunk text, which DEC-002 forbids the fixture from holding. I briefly
considered embeddings instead, and rejected it: an embedding is recoverable to an approximation of
its source, so it is content with extra steps, and it would bind fixtures to one embedding model.

So `probes.yaml` declares `matches` outright. That also draws the tool's boundary explicitly —
everything upstream is the retrieval system's business, everything downstream is the entitlement
question — which is a better answer than the one I would have written from the armchair.

The honest cost is real and now stated in the plan: a fixture cannot *observe* a retrieval system
whose relevance changes under filtering, which is exactly the mechanism behind post-filter
truncation. In a fixture that case is modelled, not measured. A passing `post-filter-truncation`
scenario shows the tool detects the shape of the failure; showing a given backend exhibits it needs
a live run.

**DEC-012 — the entitlement rule comes from the fixture.** Computing who should see what needs a
rule, and systems combine tenant, roles and direct grants differently — additive or intersecting,
tenant-scoped or global, override or union.

The reason this matters more than it looks: a tool with one hardcoded predicate is not merely
incomplete against other systems. Its wrongness surfaces as *findings* — confident reports that the
index disagrees with the source, generated by the tool misunderstanding what the source meant. That
is worse than no tool, because the output looks exactly like what the operator asked for.

Requiring the rule to be stated puts the assumption where someone can check it. The friction is the
valuable part: an organisation that cannot articulate its own entitlement rule has learned something
before a single finding is emitted.

## The layout changed

The plan specified flat `corpus/` + `index/` + `expected/`. What I built is `shared/` plus `clean/`
and `faulted/`, because keeping the two indexes as sibling files makes a planted fault a one-line
diff — self-documenting, and hard to get subtly wrong. `shared/` also needed somewhere to put the
entitlement rule, which the original layout had no slot for.

Revised the plan rather than leaving it describing a layout nothing uses.

## The checker checks the answer key, not the tool

`scripts/validate_fixtures.py` recomputes visibility from the fixture's own rule and compares it to
the authored `expected-visibility.yaml`. Hand-authored set arithmetic is wrong more often than
anyone admits, and I would rather find my own error than ship it as ground truth and spend a day
debugging a correct tool against it.

It tests the scenario, not the tool — so a future failing run means the tool is wrong rather than
the answer key. Tested both negative paths first, because a checker that has only ever passed has
not been tested. A wrong expected set is caught with both sides printed; an expected row the probes
never produce is caught as unmatched.

This is the second project where the first runnable artefact is a conformance check over authored
material rather than product code. That ordering keeps looking right: the documents make claims, and
the claims should be checkable before anything depends on them.
